# LLM-as-Judge 端到端评测管线

## 设计思路

传统评测依赖人工标注的测试集，成本高且不实时。LLM-as-Judge 使用独立的评测模型自动评分：

- 无需标注数据
- 每次对话自动触发
- 可评估相关性、有用性等主观维度
- 评测模型与回复模型解耦（`EVAL_MODEL` 可配置）：可用更便宜的模型控制成本，
  也可用更强模型提升评分稳定性；实际配置以 `.env` 为准

## 评测流程

```
用户提问 → Agent 处理 → 返回回答
                   ↓
          Evaluator.evaluate(query, answer)
                   ↓
          LLM-as-Judge（EVAL_MODEL，可配置）
          三维度评分：相关性 1-5、完整性 1-5、有用性 1-5
                   ↓
          存入 data/realtime_scores.json
                   ↓
          分数 < 3？→ 记录告警 → 触发兜底策略
```

## 三个评分维度

| 维度 | 说明 |
|------|------|
| 相关性 | 回答是否直接针对用户问题 |
| 完整性 | 回答是否覆盖问题需要的所有关键信息 |
| 有用性 | 回答是否切实解决了用户的问题 |

注意：**"三维"是三个评分维度，不是三个 prompt**——只有一个 prompt，
一次 LLM 调用同时给三个维度打分。实时评测（`app/eval/evaluator.py`）的
完整 prompt：

```text
你是一个回答质量评测助手。请严格基于以下标准评分。

用户问题：{query}
AI回答：{answer}

评分维度（1-5分）：
1. 相关性（Relevance）：回答是否直接针对用户问题？
2. 完整性（Completeness）：回答是否覆盖了问题需要的所有关键信息？
3. 有用性（Usefulness）：回答是否切实解决了用户的问题？

输出格式（仅 JSON）：
{"relevance": 1-5, "completeness": 1-5, "usefulness": 1-5, "explanation": "..."}
```

调用参数：`temperature=0.3`、`max_tokens=300`（离线批量评测脚本另有
system prompt 约束"仅输出 JSON"，且 max_tokens 已提到 500、explanation 限 50 字）。

**评分输入输出示例**：

```text
用户问题：试用期员工有没有带薪年假？
AI 回答：根据制度文档，试用期员工不享受带薪年假，年假资格自转正后按工龄计算。

评测模型输出（JSON）：
{
  "relevance": 5,
  "completeness": 4,
  "usefulness": 5,
  "explanation": "直接回答了问题，但未补充年假天数计算方式"
}
```

**低分 → 告警 → 兜底 的完整链路示例**：

```text
用户问题：出差住酒店能报多少钱？
AI 回答：可以报销。（评分：相关性 4，完整性 1，有用性 1）
→ 有用性 < 3，触发告警（写入 eval_alerts.json）
→ 触发兜底：
   1. 复用已有 RAGPipeline 重新检索（top-5，去掉 tag 限制）
   2. 把首轮工具检索结果一并拼进上下文
   3. 重新生成："出差住宿费按城市标准报销，一线城市每晚不超过 500 元……"
→ 兜底回答返回用户；兜底答案不写语义缓存（质量未二次确认）
```

## 质量保障机制

### 1. 低分告警（阈值 < 3）
当有用性或相关性低于 3 分时，系统自动：
- 记录告警到 `data/eval_alerts.json`
- 管理仪表盘显示告警数量

### 2. 自动兜底策略
检测到低分后，自动执行：
- 扩大检索范围（去掉 tag 过滤，增大 top_k）
- 复用 Agent 已有的 RAGPipeline 重新检索，**不新建 pipeline**——早期实现每次兜底
  都 new 一个 RAGPipeline（重新加载 embedding + rerank 模型），低分时反而最慢
- 首轮工具检索结果（last_tool_result）一并作为上下文，避免重复检索
- 基于更广泛的上下文重新生成回答
- 将兜底回答返回给用户
- 兜底回答不写入语义缓存（质量未二次确认，避免污染缓存）

### 3. 并发写安全
评测分数（`realtime_scores.json`）与告警（`eval_alerts.json`）都是
「读 JSON → 追加 → 写回」，`record()` 与 `check_and_alert()` 内部加线程锁，
避免并发请求交错写坏文件。

### 4. 回归基线
配置更新操作前自动保存当前评分作为基线：
- `PUT /api/admin/config/rag` 执行时保存基线
- `GET /api/admin/eval/baseline` 查看基线
- 更新后可对比更新前后的评分变化

### 5. 仪表盘可视化
管理仪表盘实时展示：
- 平均评分（相关性、有用性）环形进度图
- 告警数量（颜色编码）
- 评分趋势（来自最新评测数据）
- 详细评分列表（`/api/admin/eval/realtime`）

### 6. 离线批量评测（test-corpus）

除实时单条评测外，另有离线批量评测脚本：

- `scripts/eval_testcorpus_v2.py`：检索指标（HR@1/3/5/10、MRR、P50），
  纯本地运行，不消耗 API
- `scripts/eval_llm_judge.py`：回复质量（LLM-as-Judge 三维评分），
  复用离线检索结果生成回答并打分

评测集构建：test-corpus 企业行政文档（10 篇，67 条 QA），答案直接取自原文
（含页码/章节），可自动判定"答案是否在检索结果中"（命中判定），无需人工标注。

**评测集里一条 QA 长什么样（示例）**：

```text
文档来源：《07-薪酬与绩效管理制度.md》第四章
原文："员工持股计划的行权期为 3 年，自授予日起计算"

query：员工持股计划的行权期是多久？
answer_gt：员工持股计划的行权期为 3 年（答案必须能在原文定位，才能自动判定命中）

命中判定（以 HR@1 为例）：
  检索返回 top-1 = 包含"行权期为 3 年"的子块 → 该 query 命中，HR@1 计数 +1
  检索返回 top-1 = 不相关子块但 top-3 里有 → 该 query 未命中 HR@1（但 HR@3 命中）
```

所以"答案必须原文可定位"是评测集的关键约束：没有它就无法自动跑 HR/MRR，
只能人工标注。

**命中判定机制（为什么能自动判）**：answer_gt 是原文摘录的片段，
评测时用**子串包含**判断——`answer_gt` 是否原样出现在检索结果
（子块 content 或父块 parent_content）的文本里。因为答案取自原文，
"原文片段有没有被找回来" 就等于 "有没有找到正确答案"，无需人工标注。

**局限（面试要能说）**：字面标准偏严——改写后的答案（"五百五十元" vs
"550 元"）会被误判为未命中。所以 HR/MRR 衡量的是"原文召回能力"，
不是"回答质量"；回答质量由另一套 LLM-as-Judge（相关性/完整性/有用性）衡量。
这也是项目跑两套评测的原因：检索指标管"找没找到原文"，Judge 管"答得好不好"。

**解析鲁棒性坑**：批量评测早期按 `max_tokens=300` 限制评分输出，评测模型经常
在 explanation 处被截断；而 `extract_json` 在输出缺少右花括号时直接返回 None，
导致整条评分作废（样本率只有 62–65/67）。修复：截断时退化为逐字段提取三个维度
分数、`max_tokens` 提到 500、prompt 要求 explanation 控制在 50 字内。
修复后样本率 67/67，评测可信度显著提升。

最近一轮结果（2026-08-12）：

| 策略 | 样本数 | 相关性 | 完整性 | 有用性 | 总分 |
|---|---|---|---|---|---|
| 纯向量检索 (top-3) | 67 | 4.94 | 4.67 | 4.78 | 4.80 |
| 混合检索 (BM25+向量+RRF) | 67 | 4.99 | 4.61 | 4.79 | 4.80 |
| 混合+RRF+Cross-Encoder精排 | 67 | 4.90 | 4.60 | 4.79 | 4.76 |

注意：单轮 ±0.1 的分数差异属于 LLM 生成/评分的随机波动，结论应看多轮趋势 +
检索指标的交叉验证，不要拿单轮差值当结论。

## API 接口

| 端点 | 用途 |
|------|------|
| GET /api/admin/eval/realtime | 最新评分记录 |
| GET /api/admin/eval/summary | 聚合分数 + 告警统计 |
| GET /api/admin/eval/alerts | 低分告警列表 |
| GET /api/admin/eval/history | 历史报告对比 |
| POST /api/admin/eval/run | 手动触发批量评测 |
