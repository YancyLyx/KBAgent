# LLM-as-Judge 与三层评估体系

> 目标读者：回答"怎么评估效果"这道题的人。
> 本文档按第三篇面经的"三层金字塔"组织：分环节指标 → 主观量化 → 业务收口。

---

## 0. 破题："主观"不等于"没指标"

问答 Agent 的输出是自然语言，天然有主观性，但"主观"和"没有指标"是两回事。
成熟评估体系的核心动作是：**把主观感受翻译成可复现、可追踪、可对比的量化
指标**。面试官想听的是这个"翻译"过程，而不是"人工看效果"。

---

## 1. 第一层：分环节评估

为什么分环节：答案不好，可能是检索没召回对的资料，也可能是生成拉胯。
混在一起打分，找不到病根。分环节后，每一节单独挂指标，哪节掉链子一眼可见。

### 1.1 检索环节三把尺子

| 指标 | 一句话定义 | 它看什么 / 低了意味着什么 | 项目数字 |
|---|---|---|---|
| HR@k | 正确答案出现在前 k 个结果里的问题占比 | 该找的有没有找到；低了是召回问题 | 纯向量 HR@1 82.09% → 混合 85.07% |
| Precision@k | top-k 中与答案相关的文档占比 | 召回里有多少噪音；低了是 Rerank/Embedding 区分度不够 | 新增指标，随评测脚本输出 |
| MRR | 正确答案排位的倒数均值 | 排序质量；低了是排序不行，命中了模型也未必用得上 | 0.8799 → 0.8986 |
| P50 | 延迟中位数 | 典型响应速度 | 6.8 / 17.2 / 265.6 ms |

**为什么能脱离生成模型跑**：检索层是纯 IR 问题——准备"问题-标准文档"对照表，
自动跑 HR/MRR/Precision，不依赖大模型随机性。所以检索层优化可以做"改了就能
看到反馈"的闭环（每次改分块/换 embedding/调 Rerank 立刻出数字）。

**Precision@k 在本项目的定义**：QA 是"单答案"（answer_gt 为原文片段），
所以相关文档数 = 命中该片段的 chunk 数；P@k 在此场景衡量的是**噪音稀释程度**。

### 1.2 生成环节三件套 + 一维

| 维度 | 一句话定义 | 低意味着什么 / 怎么修 |
|---|---|---|
| 忠实度（Faithfulness） | 答案是否严格基于检索资料，有无编造 | 幻觉——RAG 最致命失败模式；改 Prompt 约束/加引用/Self-Check |
| 相关性（Relevance） | 是否答了用户真正问的问题 | 答非所问；改查询改写/强化聚焦指令 |
| 完整性（Completeness） | 是否覆盖所有关键信息 | 漏点；扩大检索/调整 prompt |
| 有用性（Usefulness） | 是否切实解决问题 | 兜底重答 |

**为什么不能合并成一个"答案好不好"的总分**：三个维度指向的优化动作完全不同，
混在一起拿到"3.2 分"不知道该往哪使劲。分开打分，问题出在哪一节清清楚楚。
（忠实度需要参考文档才能评，所以 `Evaluator.evaluate(query, answer, contexts)`
在传检索上下文时才评忠实度。）

**维度间有权衡**：Prompt 写得太严（只能逐字引用）忠实度上去、相关性可能下来
（不敢归纳）。评估体系要能看到权衡，不是单点最优。

### 1.3 交互环节指标

| 指标 | 项目实现 |
|---|---|
| 工具调用成功率 | `metrics.record_request` 记录 tool_calls/tool_failures，`summary()` 输出调用级成功率 |
| 缓存命中率 | request_metrics 聚合 cache_hit_rate |
| 告警率/兜底率 | eval_alerts + fallback 标记 |

## 2. 第二层：把"主观"翻译成结构化数据

### 2.1 Rubric（评分标准逐维定义）

评分 prompt 把每个维度写成可判断的标准（1-5 分），让不同标注员对同一条答案
能打出接近的分——Rubric 不具体，本身就变成新的主观源。

### 2.2 LLM-as-Judge 与一致性校准

**做法**：用独立评测模型（`EVAL_MODEL` 可配，与回复模型解耦）按 Rubric 打分；
传检索上下文时额外评忠实度。支持 `Evaluator.compare()` 做 Pairwise 两两比较
（相对判断比绝对打分更稳）。

**必须做一致性校准（面试分水岭）**：LLM Judge 不是黑箱。脚本
`scripts/eval_judge_calibration.py` 就绪，做两件事：
- 人工标注一致性：同批样本人工 vs Judge 逐维算 Cohen's Kappa + Pearson，
  业界经验阈值 Kappa ≥ 0.6-0.7
- Judge 稳定性（test-retest）：同一批样本跑两遍，算一致比例与 Kappa

**诚实边界（主动讲）**：校准数字需要人工标注样本（建议 ≥30 条），
本项目尚未标注，所以**没有产出校准结论**——脚本可用，数字待补。

### 2.3 Golden Set（标准评估集）

**现状**：test-corpus 10 篇制度文档 + 67 条 QA，答案全部取自原文（可自动判定
命中，无需人工标注）。这是项目能自动跑 HR/MRR/Precision 的基础。

**Golden Set 设计原则 vs 本项目现状**：

| 原则 | 现状 |
|---|---|
| 覆盖高频问题 | ✅ 制度常见问题（报销/年假/考勤） |
| 覆盖长尾问题 | ✅ 部分边界条件 |
| 覆盖陷阱问题（易幻觉/需多步推理） | ⚠️ 未分类标注 |
| 覆盖安全问题（合规/敏感必须拒绝） | ⚠️ 未分类标注 |
| 规模适中（200-500 甜区） | ⚠️ 67 条偏小，扩展集待建 |

**边界**：Golden Set 一旦定下来不能随便改（破坏历史可比性）；新增问题走扩展集，
老问题标准答案锁版本。

## 3. 第三层：业务指标收口（"所以呢"）

技术指标做得再漂亮，业务方关心结果。传导链：

```
Recall↑ → 准确率↑ → 解决率↑ → 升级率↓ → 成本↓
```

四类业务指标：满意度（CSAT/NPS/点赞率，看趋势不看绝对值）、解决率（FCR/
任务完成率）、升级率（人工升级率/投诉率）、成本（单次会话成本/Token）。

**诚实边界（主动讲）**：单机项目没有真实用户流量，满意度/解决率/升级率
**没有产出数字**。能讲的是：这套评估体系上线后如何挂这些指标（埋点已支持
token 成本、工具成功率、告警率），以及四类指标之间的张力（压升级率满意度可能
掉，答案更详细 token 成本上升）——评估收口的本质是在四类指标间找均衡点。

## 4. 实时评测链路（低分 → 告警 → 兜底 → 回溯）

```
用户提问 → Agent 处理 → 返回回答
  → Evaluator.evaluate(query, answer, contexts=检索结果)
     四维评分：相关性 / 完整性 / 有用性 / 忠实度（有上下文时）
  → 存入 data/realtime_scores.json（含 memory_context 与 faithfulness）
  → 任一维度 < 3 → 告警（eval_alerts.json）
      → 兜底：复用已有 pipeline 扩大检索（去掉 tag 限制、top-5）
             + 首轮检索结果一并拼上下文 → 重新生成
             → 兜底答案不写缓存
  → 低分告警的 query/answer/memory_context 可回溯 badcase
```

**为什么传 contexts 评忠实度**：忠实度的定义是"答案是否基于检索资料"，没有
参照物无法评。传 `last_tool_result`（本轮检索结果）后，Judge 能判断
"这段答案是检索来的还是编的"。

**badcase 回溯闭环**：告警记录含 query/answer/三维分数/忠实度/注入的记忆片段
（memory_context）——定位"是不是某条记忆污染带偏了回答"成为可能。

## 5. 工程取舍（六条，架构师视角）

| 取舍 | 本项目选择 / 说明 |
|---|---|
| 自动 vs 人工配比 | 当前全自动（LLM Judge）；关键维度人工抽检 + 争议双盲是演进方向 |
| Golden Set 规模 vs 维护 | 67 条偏小；扩展集待建，老问题锁版本 |
| Judge 模型选择 | EVAL_MODEL 独立配置（可用更便宜模型控成本）；中等模型初筛 + 强模型复核是演进方向 |
| 评估频率 | 检索层离线脚本可挂 CI（秒级）；生成层批量脚本 nightly；业务指标周报（需线上） |
| 在线 vs 离线 | 离线是门槛（Golden Set + Judge），在线是裁判（A/B）；本项目只有离线，诚实标注 |
| 告警阈值 | 当前绝对阈值（维度 <3 告警）；基于历史基线方差的分维度漂移告警是演进方向 |

## 6. 面试话术（三层结构 + 一升华）

> 第一层（基本原理）：主观是客观存在的，但成熟做法是分层拆解——检索/生成/
> 交互三环节各挂独立指标，检索看 HR/MRR/Precision，生成看忠实度/相关性/
> 完整性/有用性，交互看工具成功率。
> 第二层（细节为什么）：分开是因为混在一起打分找不到病根；主观评估要结构化
> 是因为笼统打分不可复现；LLM Judge 要一致性校准是因为不校准就是另一个黑箱。
> 第三层（设计哲学）：评估的本质不是"测准不准"，而是把主观感受翻译成可追踪
> 的数据——翻译能力才是工程化的核心。
> 升华：技术指标最终收口到业务指标（满意度/解决率/升级率/成本），
> 形成"技术驱动业务"的闭环。

**加分项**：一致性校准、Golden Set 四类覆盖（诚实说缺口）、离线 vs 在线边界、
指标权衡。
