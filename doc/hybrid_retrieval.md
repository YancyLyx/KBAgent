# 多策略混合检索（RRF + 重排序）

## 检索管线

```
用户查询 → 混合检索（向量 + BM25 → RRF 合并）
  ↓
Top-N 候选 → CrossEncoder 重排序 → Top-K 结果 → LLM
```

**为什么需要混合检索（一个具体例子）**：

```text
用户问：员工持股计划的行权期是多久？
文档原文：员工持股计划的行权期为 3 年，自授予日起计算

纯向量检索：靠"语义相近"匹配。"行权期"是低频专有名词，语义上
  和"授予""锁定期"都不太近，向量相似度可能排不进 top-3 → 漏召回

纯 BM25：靠"词精确命中"。"行权期"三个字在原文里原样出现，
  关键词打分很高 → 必然命中，但反过来对"休假怎么算"这种
  说法换了个词的问题（"带薪年假"vs"年假怎么休"）无能为力

混合检索：向量管"意思差不多"，BM25 管"词原样命中"，RRF 按排名融合，
  两路都命中的文档得分最高 → 专有名词和同义改写都能兜住
```

一句话：**向量负责"懂意思"，BM25 负责"认字面"，单路都会漏，合起来才稳**。

## 四层结构

### 1. 语义级分块
文档首先按章节边界解析为语义父块：
- **PDF**：字号分析检测标题（1.3 倍正文 → 子标题，1.8 倍 → 章标题），pdfplumber 提取表格并序列化，图片标题从邻近文本提取
- **Markdown**：按 #/##/### 标题层级分块
- **纯文本**：RecursiveCharacterTextSplitter 兜底

### 2. 父子切割
每个父块进一步切分为子块（RecursiveCharacterTextSplitter，当前配置
`child_chunk_size=300`；离线评测脚本对比过 150 字版本）。子块用于检索匹配（精度），
父块作为 LLM 上下文（完整性）。

**为什么父子分块而不是单层分块**：单层大块（如 1000 字）检索时，一个 chunk 里
可能只有一小段相关，向量/BM25 分数被无关文字稀释，且 top-k 命中后整块喂给 LLM
浪费 token；单层小块（如 150 字）精度高但上下文断裂，LLM 拿不到完整章节。
父子方案取两者之长：子块做精确匹配（召回准），命中后按 `parent_id` 去重、
返回父块（上下文全）。代价是多存一层索引 + 去重逻辑，换来的是"召回精度"和
"上下文完整性"同时成立。

**完整检索顺序**：

```text
① 混合检索（向量 + BM25 → RRF）——在【子块】层面检索，找 top-N 个子块
② 按 parent_id 去重——同一父块下命中多个子块，只保留分数最高的一个
③ 回填父块内容——返回 metadata.parent_content，而不是子块本身
④ （可选）CrossEncoder 精排——在父块列表上再排一次
⑤ 返回父块列表给 LLM
```

**metadata 是什么**：向量库里每条记录除"文本 + 向量"外的结构化附属字段
（键值对，子块入库时写入、检索时随结果返回）。父子流程依赖其中三个：
`parent_id`（指向所属父块，去重靠它）、`parent_content`（父块全文，回填靠它）、
`parent_section`（来源章节，回答标注出处）。tag 过滤也是靠 metadata 里的 tag 字段。

**BM25 结果为什么必须带 metadata**：向量检索（Chroma）天然返回 metadata，
但 BM25 是独立维护的内存索引、默认只存文本。若 BM25 结果不带 metadata，
keyword-only 命中的子块拿不到 parent_id，无法去重和回填父块，只能把子块自己
当父块返回给 LLM（上下文断裂，即"坑 5"）。

### 3. 混合检索 + RRF 合并

双路并行检索：

| 引擎 | 模型 | 优势 |
|------|------|------|
| 向量 | bge-small-zh（余弦相似度） | 语义匹配，同义词处理 |
| 关键词 | rank-bm25（BM25Okapi） | 精确匹配，专有名词，罕见实体 |

**中文分词（bigram）**：BM25 索引对 CJK 连续串按重叠二元组（bigram）分词，
英文/数字按单词处理。不能直接用 `\w+`——中文没有空格，整句会变成一个 token，
导致「差旅报销」永远匹配不上「差旅报销标准为每晚 400 元」。选 bigram 而不是
jieba 的理由：零依赖、速度快、对领域新词不敏感；代价是少量匹配噪音，由混合检索
的 RRF 排序和 CrossEncoder 精排兜底。

**BM25 打分原理（公式 + 手算 + 项目实现）**：

BM25 是信息检索经典的 TF-IDF 家族模型，对查询 Q 和文档 D 的相关性打分：

```
score(D, Q) = Σ   IDF(q) × [ tf(q,D) × (k1+1) ]
             q∈Q        ─────────────────────────
                        tf(q,D) + k1 × (1 - b + b × |D|/avgdl)

IDF(q) = ln( 1 + (N - n(q) + 0.5) / (n(q) + 0.5) )
```

三个因素的作用：

| 因素 | 含义 | 效果 |
------|------|------|
| IDF（逆文档频率） | 词 q 出现在多少篇文档里（n(q)），N 为文档总数 | 词越稀有权重越高 |
| tf（词频） | 词在文档中出现次数 | 出现越多越相关，但 k1=1.5 让分数非线性饱和 |
| 长度归一化 | \|D\|/avgdl（文档长度 ÷ 平均长度），b=0.75 控制强度 | 长文档的词频打折，避免长文档天然占便宜 |

**手算示例（查询"行权期"，3 篇文档）**：

```text
D1: 员工持股计划的行权期为 3 年   （12 个 token）
D2: 差旅报销标准为每晚 400 元     （10 个 token）
D3: 行权期结束后股票归属          （8 个 token）
查询 "行权期" → ["行权", "权期"]
```

```text
第 1 步 IDF："行权"/"权期"都出现在 D1、D3（n=2），N=3
  IDF = ln(1 + (3-2+0.5)/(2+0.5)) = ln(1.6) ≈ 0.470

第 2 步 逐篇打分（k1=1.5, b=0.75, avgdl=(12+10+8)/3=10）：
  D1：tf=1, |D|=12 → 长度因子=1-0.75+0.75×12/10=1.15
      每个词得分 = 0.470×2.5/(1+1.5×1.15) ≈ 0.431 → 总分 ≈ 0.862
  D3：tf=1, |D|=8  → 长度因子=1-0.75+0.75×8/10=0.85
      每个词得分 = 0.470×2.5/(1+1.5×0.85) ≈ 0.516 → 总分 ≈ 1.033
  D2：两个词 tf 都为 0 → 0 分，被 score≠0 过滤
```

结果 D3 > D1 > D2：两篇都命中时，更短的文档在长度归一化后得分更高；
完全没命中的 D2 排除。RRF 融合只看排名不看分数绝对值，所以 0.431 与 0.516
的差距不影响融合结果。

**项目里的检索流程**：

```text
建索引（入库时 _rebuild_bm25）：
  ChromaDB 全量读子块文本 → bigram 分词 → BM25Okapi(corpus) 建内存索引
  （预计算每篇文档的 token 列表与平均长度）

查询（bm25_search）：
  查询 bigram 分词 → get_scores() 对全部文档逐篇套公式打分（O(N)，毫秒级）
  → tag 过滤（只算指定分类）→ 分数降序取 top_k
  → 结果带 metadata（父子分块去重依赖 parent_id）
  → score≠0 才保留（小语料下高频词 idf 可能为负，真实命中也是负分，不能按 >0 过滤）
  → 排名交给 RRF 与向量检索融合
```

两路结果通过 **Reciprocal Rank Fusion (RRF)** 合并：

```
Score(d) = Σ 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在系统 i 中的排名，`k` 为常数（默认 60）。

RRF 优于加权分数合并的原因：
- **基于排名而非分数**：不同检索引擎的分数分布不可比，排名可比
- **鲁棒性强**：不受向量与 BM25 分数分布差异影响
- **业界标准**：Elasticsearch、Vespa 等现代搜索引擎采用的方式

**数值示例（k=60，两个引擎各取前 2 名）**：

```text
向量引擎排名：① 文档A  ② 文档B
BM25 引擎排名：① 文档B  ② 文档C

文档A：1/(60+1) = 0.01639
文档B：1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 = 0.03252  ← 两路都命中，分最高
文档C：1/(60+2) = 0.01613
```

可以看到：文档 B 在两个引擎里都排进前 2，融合后总分最高——RRF 奖励"多路都认为
相关"的文档，而不是某一路分数高但另一路完全没命中的文档。这就是混合检索能
同时吃掉"语义相似"和"关键词精确"两类信号的原因。

### 4. CrossEncoder 重排序
RRF 合并后的 Top-N 候选由 bge-reranker-base CrossEncoder 重新打分。每对 (query, document) 联合编码计算精确相关性。作为质量关卡：语义相似但与问题无关的文档在此被过滤。

## Advanced RAG 增强（查询/生成/重排层优化）

在混合检索 + 精排之上，支持四项 Advanced RAG 增强：

| 增强 | 模块 | 解决什么 | 启用方式 |
------|------|---------|---------|
| 上下文压缩 | `app/rag/context_compressor.py` | 超长工具/检索结果先用 LLM 压缩保留关键信息，替代简单截断（避免切句丢数字） | Agent 工具结果超预算自动触发，失败回退截断 |
| 多查询分解 | `app/rag/query_expansion.py` | 复杂问题（"差旅和餐补分别怎么规定"）拆子查询分别检索、合并去重 | search_knowledge_base 命中规则（含分别/对比/哪些等词或长查询）自动触发 |
| HyDE 假设答案检索 | `app/rag/query_expansion.py` | 用 LLM 生成假设答案参与检索，答案文本与文档更相似 | 与多查询同路径，作为额外候选 |
| MMR 去冗余 | `app/rag/mmr.py` | 重排后 top-k 语义重复，按相关性与多样性平衡重新选择 | `RAGPipeline.retrieve(diversity_rerank=True)` |
| 相关性阈值过滤 | `Reranker.rerank(threshold=...)` | 重排后剔除低分文档，避免噪声进 LLM | `RAGPipeline.retrieve(min_rerank_score=...)` |
| Autocut 分数悬崖动态截断 | `Reranker.rerank(autocut=True)` | 重排后找相邻文档最大相对分数落差，落差处截断——替代"固定 TopK 全收"的噪声注入 | `RAGPipeline.retrieve(autocut=...)`；`retrieval_strategy.autocut` 配置默认关 |
| Self-RAG 检索反思 | `AgentManager._search_with_self_rag` | 检索后 LLM 判断片段是否足够回答；不足则生成改写查询补检（内容去重合并，无新增即停）——Agent 驱动迭代检索的反思环节 | `loop_config.yaml` 的 `self_rag.enabled` 默认关 |

四项均默认关闭/按需触发，不影响默认检索路径与既有评测数据。

## 标签感知过滤

通过 Skill 系统指定 tag 时，向量检索（ChromaDB `where` 过滤）和 BM25 检索（`_bm25_metas` 逐条验证）都只返回匹配分类的结果，从源头消除跨分类噪声。

**BM25 过滤的坑**：BM25 索引与向量库是两套独立结构，早期实现 BM25 检索忽略 filters，
按 tag 检索时 keyword-only 命中的文档会混入其他知识库；同时 BM25 结果不带 metadata，
父子分块去重拿不到 `parent_id`，BM25 命中的子块会退化成"子块当父块"直接给 LLM。
现在 `bm25_search` 支持 filters 且每个结果都携带完整 metadata，混合检索合并时保留。

**坑 1 示例：按 tag 检索混入其他知识库**

```text
用户问"行权期"，Skill 路由到股权激励库 → search_knowledge_base(query, tag="股权激励")

向量检索（Chroma where）：
  where={"tag": "股权激励"} → 只在股权激励库内找 ✅

早期 BM25（忽略 filters）：
  在整个知识库（含差旅报销/薪酬绩效等）打分
  → 差旅报销库里有篇文档含"行权"两个字（如"行权期内差旅费可报销"）
  → BM25 命中它，RRF 融合后进入结果 → 回答混入了无关分类的内容 ❌

修复后：bm25_search 先按 metadata 逐条验证 tag == "股权激励"，
  再打分排序 → 与向量检索过滤口径一致 ✅
```

**坑 2 示例：keyword-only 命中丢失父块上下文**

```text
父子分块：父块 = 完整章节，子块 = 章节里切出的小段（metadata 带 parent_id/parent_content）

查询"行权期"：
  → 向量检索命中子块 A（带 metadata）→ 去重时能拿到 parent_id → 回填父块 ✅
  → BM25 命中子块 B（早期结果只有 content，没有 metadata）
     → parent_child_search 去重时拿不到 parent_id
     → 只能把"子块 B 自己"当作父块返回给 LLM
     → LLM 只看到一小段，看不到完整章节 → 上下文断裂 ❌

修复后：bm25_search 每个结果带完整 metadata（含 parent_id/parent_content），
  混合合并时保留 → keyword-only 命中也能正确回填父块 ✅
```

**小语料 idf 为负**：BM25 原始公式在小语料下高频词 idf 为负，真实命中的分数也可能
小于 0。检索结果按 `score != 0`（即查询词确有出现）过滤而不是 `score > 0`，避免
把真实命中全部丢掉；RRF 只看排名不看绝对值，负分不影响融合结果。

**文档删除/重索引**：删除文档时通过 `delete_by_metadata({"source": 文件名})` 同步清理
向量分块并重建 BM25 索引（ChromaDB 支持 where 删除），重索引前先清旧分块再入库，
避免「文件已删但检索仍能召回」和「重复索引」两类脏数据。

## 召回率低怎么排查（Checklist）

面试官问"召回率低你从哪几方面排查"，按下面的顺序讲：

1. **先确认答案在库里**：检查分块是否丢内容（答案保留率，本项目 test-corpus 为
   97%）。丢内容 → 分块器/解析器问题，不是检索问题。
2. **单路跑分**：分别看纯向量和纯 BM25 的命中情况，判断是哪一路在拖后腿。
   向量差 → 换 embedding / 加同义词扩展；BM25 差 → 查中文分词（本项目踩过
   `\w+` 整句一个 token 的坑，改 bigram 后修复）。
3. **看过滤条件**：tag 过滤是否误伤（BM25 早期实现忽略 filters，混库/漏检并存）。
4. **放大候选再精排**：混合检索 top_k 放大（3×）→ RRF 融合 → CrossEncoder 精排，
   精排分数分布能看出"候选集里有没有对的，只是没排上来"。
5. **Badcase 回流**：把漏检 query + 正确答案补进评测集，作为回归用例，
   改完检索策略后重跑，防止修好一个坏掉另一个。

## 检索指标补充：Precision@k 与三个深度问题

**Precision@k（精确率）**：top-k 中与标准答案相关的文档占比。
本项目 QA 是单答案（answer_gt 为原文片段），相关文档数 = 命中该片段的 chunk
数，所以 P@k 在此场景衡量的是**噪音稀释程度**——top-k 里无关内容占比越高，
说明 Rerank/Embedding 区分度不足，噪声越可能带偏 LLM。
（HR 看"有没有命中"，MRR 看"排得靠不靠前"，Precision 看"召回回来多少噪音"，
三把尺子合起来才是完整画像。）

**三个深度问题（面试自测，附项目答案）**：

| 问题 | 答案 |
|---|---|
| Q1 向量相似度很高但答案不在召回里 | 双塔 embedding 是"语义相近"，不是"精确匹配"——像 `WO-8827391` vs `WO-8827392` 这种实体号在向量空间几乎重合，语义相近但不是一个东西。KBAgent 的"行权期"是同类问题（低频专有名词向量排不进 top-3），解法是多路检索：BM25+bigram 精确命中兜住（HR@1 82→85% 就是证据） |
| Q2 召回 100% 对但 LLM 答错 | 生成层幻觉，属于生成问题不是检索问题。工程只能缓解：忠实度评测（Judge 传检索上下文评 1-5）+ 低分告警兜底 + 引用来源约束；根除不了，面试要诚实说 |
| Q3 离线指标提升但线上满意度降 | 评测集与真实用户分布偏差（问法/长尾/场景不同）。KBAgent 自己的数据就是例子：精排 HR@1 +1.5pp，但 LLM-as-Judge 三维分无提升 → 默认关闭精排。真正的线上裁判是 A/B 测试，这是演进方向 |

## 检索侧的工程取舍（架构师视角）

| 取舍 | 本项目选择 | 为什么 |
|---|---|---|
| RRF 融合权重：固定 vs 动态 | 固定 k=60 | 两路分数分布不可比，排名可比；文章建议初期固定、积累数据后再按 query 类型（如含精确编号）动态切换 |
| 查询改写次数 | 最多一次（分解+HyDE 各一次），失败回退原查询 | 每改写一次多一次 LLM 调用、延迟翻倍；二次改写边际收益低 |
| 候选放宽：固定阈值 vs 多召回 | 先放大 top_k×3 再精排；Autocut/阈值过滤在精排后 | "没有高分结果"≠"没有相关内容"——先多召回让模型判断，别死守阈值 |
| 精排是否默认开 | 默认关 | 数据决策：HR@1 +1.5pp 换 15 倍延迟，且生成质量无提升 |
| Autocut 阈值 | drop_ratio=0.3 可配，默认关 | 相对落差 30% 以上视为断层；需 67 条评测对比后再定默认值（待办，不假装） |
