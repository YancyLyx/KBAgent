# 跨会话语义记忆系统

## 架构概览

```
┌─────────────────────────────────────────────────────────┐
│                   AgentManager.chat()                    │
├─────────────────────────────────────────────────────────┤
│  在 LLM 调用前注入：                                      │
│    1. 短期记忆（deque，最近 N 轮，当前配置 10）          │
│    2. 语义召回（ChromaDB，跨会话相关片段）               │
│    3. 演进式摘要（SQLite，最新版本）                     │
│    4. 用户画像（SQLite，提取的事实）                     │
├─────────────────────────────────────────────────────────┤
│  在 LLM 回复后执行：                                      │
│    1. 保存到短期记忆（deque）                            │
│    2. 保存到 ChromaDB（对话记忆）                        │
│    3. 每 N 轮（短期记忆窗口边界，N=max_history_length）  │
│       更新演进式摘要 + 提取用户画像                      │
├─────────────────────────────────────────────────────────┤
│  存储层：                                                │
│    短期记忆：deque（内存，maxlen=N 轮）                   │
│    对话记忆：ChromaDB（向量库，支持语义检索）             │
│    摘要：SQLite（conversation_summary 表）               │
│    画像：SQLite（user_profile 表）                       │
└─────────────────────────────────────────────────────────┘
```

## 存储策略：为什么同时用 ChromaDB 和 SQLite

| 数据 | 存储 | 检索方式 | 理由 |
|------|------|---------|------|
| 对话历史（每轮对话） | ChromaDB | 语义相似度搜索 | 用户新问题需要"语义上最相关"的历史片段，跨会话 |
| 演进式摘要 | SQLite | 精确查询 | 按 user_id 取最新一条：`ORDER BY created_at DESC LIMIT 1` |
| 用户画像 | SQLite | 原子更新 | 需要读→修改→写的事务性操作 |
| 短期记忆 | 内存 deque | FIFO | 最近 N 轮，无需持久化 |

**ChromaDB 负责语义检索**。对话历史存为向量，支持跨会话语义召回——用户问"上次说的认证方案是什么？"时，能在全部历史对话中找到语义最相关的那段，不依赖关键词匹配。

**SQLite 负责结构化查询**。摘要和画像的访问模式是精确查询（按 user_id、按时间排序、COUNT 聚合），这些是 SQL 的强项。硬塞进 ChromaDB 意味着全量扫描后在内存里手动排序分页，慢一个数量级。

两者互补，不是冗余。这也是生产环境的标准选型。

## 组件详解

### 1. 短期记忆（会话上下文）

- 实现：`collections.deque`，`maxlen = max_history_length × 2`
- deque = 双端队列，这里用作"固定长度的滑动窗口"：满了从一端塞入时自动从另一端
  挤掉最旧的，天然适合"只保留最近 N 轮"
- 默认值：最近 10 轮（20 条消息：10 用户 + 10 助手），通过 `memory_config.yaml` 配置
- 通过 `memory_config.yaml` 的 `short_term_memory.max_history_length` 配置
- 写入时机：每轮对话（含缓存命中轮）回复后写入
- 召回时机：构造本轮 LLM messages 前，作为「对话历史」注入 system prompt

### 2. 长程对话记忆（ChromaDB 向量库）

- 存在于 ChromaDB 的独立 collection 中
- 每次对话的 user 和 assistant 消息都存为一条记录，包含文本 + embedding
- 每次新对话时，自动对当前用户的历史对话做语义检索（top 3）
- 相关片段注入 system prompt，并标注"供参考，不要直接引用为事实"，
  防止记忆污染事实（见下方解释）
- 跨会话：检索范围不限于当前 session，追溯全部历史
- 写入时机：每轮回复结束后写入 user + assistant 两条
- 召回时机：每轮开始前按当前问题做语义检索（top 3）

**为什么标注"不要直接引用为事实"（示例）**：

语义回忆的片段是**用户历史对话**，不是知识库文档——对话里的话可能记错、
随口说、是假设或草稿，不能当作事实依据。注入格式：

```text
## 相关历史对话片段
- [user] 上次说的那个认证方案，后来部署到 K8s 了吗？
- [assistant] 我们讨论了 JWT 认证，计划部署到 K8s……
（以上历史片段供参考，不要直接引用为事实）
```

```text
场景：用户上次说"差旅住宿标准好像是 800 元吧"（记错），
      知识库文档实际是 400 元。

不标注：模型把片段当事实 → 回答"标准是 800 元" ❌ 记忆污染事实
有标注：模型把片段当线索（理解用户在说差旅报销、延续话题），
        回答以知识库检索结果为准 → "标准是 400 元" ✅
```

一句话：**记忆片段是"线索"不是"依据"**——用来理解指代和延续话题，
事实必须来自知识库检索。

### 3. 演进式摘要（每 N 轮更新一次，N = 短期记忆窗口大小）

参考 Claude/Codex 的上下文压缩机制，不是每 N 轮独立生成一条，而是始终只有一条摘要，逐轮演进：

```
第 10 轮：LLM 读取 "当前摘要：(空)" + "新增 10 轮"
         → 输出 "用户正在开发 API，需要 JWT 认证方案"

第 20 轮：LLM 读取 "当前摘要：(旧摘要)" + "新增 10 轮"
         → 输出 "用户选用 JWT 认证，部署到 K8s，遇到性能问题"

第 30 轮：LLM 读取 "当前摘要：(旧摘要)" + "新增 10 轮"
         → 输出 "用户解决连接池问题，新增日志监控需求"
```

每次 LLM 将旧摘要（覆盖全部历史的关键信息）与新增对话合并，输出新摘要替代旧摘要。早期上下文不会丢失，因为 LLM 每次都将关键信息带到新摘要中。

**历史保留与清理**：`conversation_summary` 表按"插入新行"演进，`get_running_summary`
只读最新一版；旧摘要不物理删除（Chroma 快照 + 表内历史行），但**每个用户只保留
最近 `summary.keep_recent`（默认 20）行**，防止表无限增长——再老的版本靠
Chroma 快照语义召回，不占用 SQLite。

**为什么触发时机是窗口边界而不是固定轮数**：短期记忆 deque 只保留最近 N 轮，
第 N+1 轮进来时第 1 轮就被挤掉了。如果触发间隔大于 N，被挤掉的那几轮在总结前就
已从窗口消失，永远进不了摘要（早期实现用 `ShortMemory.get_turn_count()` 判断，
但它返回的是窗口内剩余轮数，窗口填满后恒为 N，`% 10` 的触发条件要么永不成立、
要么填满后每轮都触发，都是错的）。现在由 AgentManager 维护会话累计轮数
`_session_turn_count`，在第 N、2N、3N……轮用「旧摘要 + 窗口内 N 轮」合并，
滑出窗口的每一段对话都被覆盖。

**窗口滑动示例（N=10）**：

```text
第 10 轮结束：窗口 = [1, 2, ..., 10]  → 触发摘要：空摘要 + 第 1-10 轮 → 摘要 A
第 11 轮进来：deque 挤掉第 1 轮，窗口 = [2, 3, ..., 11]
第 20 轮结束：窗口 = [11, 12, ..., 20] → 触发摘要：摘要 A + 第 11-20 轮 → 摘要 B
第 21 轮进来：deque 挤掉第 11 轮，窗口 = [12, ..., 21]
```

第 1-10 轮的内容在第 10 轮就被收进摘要 A，之后窗口怎么滑都不会丢；
如果不触发，第 11 轮就把第 1 轮挤掉，那部分对话就永久丢失了。

**面试话术：上下文窗口满了怎么办**（把三层策略串起来）：

> "短期记忆用滑动窗口，满了挤掉最旧的；但挤掉之前会做演进式摘要，把窗口内容
> 压缩成一条长期状态，所以旧信息不是丢失而是被压缩；再往前的历史通过向量库
> 语义召回，用户问'上次说的那个方案'时按相关性把最相关的片段捞回来注入。
> 三层分别解决'近'、'中'、'远'的记忆，成本可控，且不会一次性把上下文塞满。"

**进程重启安全**：对话记忆的轮次序号（turn_index）如果只存在内存里，重启后重新从 0
计数会与已入库记录撞 ID（ChromaDB 对重复 ID 直接抛异常，导致整轮写入失败）。
现在写入前会先查询该会话在 ChromaDB 中的最大 turn_index 并恢复计数，且 doc_id 带
uuid 后缀，双保险保证重启后写入不失败。

**示例（重启前后到底发生了什么）**：

```text
重启前（进程 A）：
  会话 s1 已写入 3 轮，Chroma 里的 doc_id（turn_index + uuid 后缀）：
    s1_0_ab12cd34、s1_1_ef56ab78、s1_2_cd34ef56
  → 内存里的 _turn_counter["s1"] = 3

服务重启（进程 B）：
  _turn_counter 随内存清空（不再记得 s1 已经写到 2）

修复前（doc_id 只有 turn_index、没有 uuid）：
  第 4 轮写入 doc_id = "s1_0"（从 0 重新数）
  → ChromaDB DuplicateIDError（s1_0 已存在）→ 整轮写入失败 → 接口 500

修复后：
  第 4 轮写入前先查 Chroma：s1 现有记录的最大 turn_index = 2
  → 恢复计数 _turn_counter["s1"] = 3
  → 写入 doc_id = "s1_3_9f0e1d2c"（turn_index=3 + 新 uuid）
  → 即使恢复逻辑出问题，uuid 后缀也保证 doc_id 全局唯一，不会撞
```

一句话：**计数恢复解决"从几号开始写"，uuid 解决"万一数错了也不会撞"**。

### 4. 用户画像（同一次 LLM 调用提取）

与演进式摘要同一次 LLM 调用，返回结构化 JSON：

```json
{
  "summary": "更新后的摘要...",
  "user_profile": {
    "role": "开发工程师",
    "key_facts": [
      {"text": "偏好 Python 示例", "updated_at": "2026-08-12T20:00:00", "source": "summary_extraction"},
      {"text": "使用 K8s 部署", "updated_at": "2026-08-12T20:00:00", "source": "summary_extraction"}
    ]
  }
}
```

画像数据存入 SQLite `user_profile` 表（**当前生效版本**），后续对话注入 system
prompt 前按时间倒序、场景匹配、条数与长度截断（默认最多 5 条、每条 80 字），
控制注入篇幅。每次更新同时 append 一条人可读审计日志到
`data/profiles/{user_id}.md`（**变更历史**），记录变更前后、来源与时间——
SQLite 管"当前状态"，MD 管"可审计历史"，两者分工。

**偏好不一致怎么处理（四类场景）**：

| 场景 | 处理 |
------|------|
| 用户明确改口 | 新时间戳覆盖旧条目，旧条目留在审计 MD 里 |
| 场景相关（如上班/私人偏好不同） | 不覆盖：不同偏好合并并存，条目带场景字段时按当前场景匹配注入 |
| 误提取（把文档内容当用户偏好） | 纠错闭环：低分告警回溯注入片段、管理端可查 MD 审计并人工删改、注入时标注"仅供参考" |
| 乱序覆盖（旧请求晚到） | 乐观锁：同文本只有新时间戳 ≥ 当前值才允许覆盖，否则丢弃 |

核心规则一句话：**同文本按"新时间戳覆盖旧时间戳"，不同文本合并并存，
所有变更留审计**。

**存储与格式（示例）**：

当前状态存在 SQLite（`user_profile.preferences` 字段，JSON），
历史追加写 MD 审计（`data/profiles/{user_id}.md`），两者分工：

```text
SQLite 当前状态（JSON）：
  preferences = {
    "extracted_facts": [
      {"text": "偏好 Python 示例", "updated_at": "2026-08-12T20:00:00", "source": "summary_extraction"}
    ]
  }

data/profiles/u1.md 审计历史（每次变更追加一条）：
  ## 2026-08-12T20:00:00  source=summary_extraction
  变更前：{"preferences": {"extracted_facts": []}}
  变更后：{"preferences": {"extracted_facts": [{"text": "偏好 Python 示例", ...}]}}
```

**当前判重逻辑**：没有独立的 key 字段，合并按 `text` **精确匹配**
（`_merge_fact_list` 用文本做去重键）。所以：

```text
"偏好 Python 示例" vs "偏好 Python 示例"  → 同文本 → 时间戳新的覆盖旧的 ✅
"偏好 Python 示例" vs "偏好 Go 示例"      → 不同文本 → 并存（上一条已知边界）⚠️
"示例用 Python"    vs "偏好 Python 示例"  → 表述差几个字 → 也并存 → 同一偏好重复 ⚠️
```

当前实现没有 key 字段，也没有模糊匹配，合并键是文本精确相等——
同一偏好只要表述差一两个字就会被当成两条并存，这是真实缺陷，需改进。

**三个可选方案**：

| 方案 | 做法 | 优点 | 代价 |
------|------|------|------|
| A. 语义去重（推荐） | 写入时把新 fact 与已有 facts 两两算 embedding 余弦，≥0.92 视为同一条 → 更新旧条目（刷新文本/时间戳），否则新增 | 零额外 LLM 调用；"差一两个字"、"换个说法"都能归并 | 每次画像更新多一次 embedding（低频，每 10 轮一次，可接受）；阈值可能误并（语义相似但确实不同） |
| B. LLM 判断合并（Mem0 式） | 写入时让 LLM 判断新事实 vs 现有列表：新增 / 更新哪条 / 删除哪条 | 最准，能处理"改口"和"纠正" | 每次写入多一次 LLM 调用（最贵）；LLM 判断本身可能错 |
| C. key-value 主题模型 | fact 增加 key（如"示例语言"），同 key 只保留最新值；key 由 LLM 提取并归一化 | 结构最清晰，注入可按主题去重 | key 归一化依赖 LLM 输出质量；key 差一两个字仍要靠语义去重兜底 |

推荐组合：**A + C**——LLM 提取时给 fact 打 key（主题），写入时用语义相似度做
归并（兜底 key/文本表述差异），注入时按 key 去重只取最新。成本只多一次 embedding，
却能同时解决"差一两个字"、"换个说法"、"同一主题改口"三类问题。

**四类场景的完整示例（含当前实现的边界）**：

```text
① 用户明确改口
   第 1 轮：用户说"示例都用 Python" → 写入「偏好 Python 示例」@T1
   第 30 轮：用户说"还是改成 Go 吧" → 写入「偏好 Go 示例」@T2（T2 > T1）
   结果：两条文本不同，按当前规则【并存】，注入时可能同时出现——这是已知局限。
   改进方向：按偏好主题（key，如"示例语言"）合并，同一主题只保留最新时间戳，
   而不是按文本合并。面试被追问时如实说明。

② 场景相关（不是冲突）
   用户："上班用公司模板，自己项目用 Python"
   → 写入「偏好：公司模板（scene=工作）」「偏好：Python（scene=个人）」
   结果：两条并存、各带 scene 字段；注入时按当前对话场景匹配，互不覆盖。

③ 误提取（LLM 把文档内容当用户偏好）
   文档里写着"公司统一采用 JWT 认证"，LLM 提取时误写入画像
   → 审计 MD 里能看到 source=summary_extraction、时间、变更前后
   → 管理端 `DELETE /api/admin/memory/{uid}/facts` 按文本删除该条目
   → 低分告警 + Badcase 回溯是"发现"入口，人工删改是"修正"手段。

④ 乱序覆盖（旧请求晚到）
   请求 A（用户改口 Go）先发出但网络慢，请求 B（改口 Rust）后发出先落库
   → B 写入「偏好 Rust 示例」@T2
   → A 随后到达，携带「偏好 Go 示例」@T1（T1 < T2）
   → 乐观锁：同文本比较时间戳，T1 < T2 拒绝覆盖，保留「Rust」
```

这个示例特意暴露了第 ① 类的边界：当前实现能防"旧覆盖新"和"场景互踩"，
但"同一主题的不同取值"会并存——知道这个边界并给出改进方向，
比假装完美更经得住面试追问。

## 记忆的写入/召回时机总览

**触发事件视角（回答"什么时候触发读写"）**：

| 触发事件 | 写什么 | 读什么 |
|---------|--------|--------|
| 每轮回复后（**缓存未命中**） | 短期记忆写入本轮对话；对话记忆（Chroma）写入 user + assistant 两条；话题计数更新 | — |
| 每轮 LLM 调用前（**缓存未命中**） | — | 短期记忆（最近 N 轮）+ 语义回忆（Chroma top-3）+ 演进式摘要 + 用户画像，全部注入 system prompt |
| 窗口边界（第 N、2N、3N 轮，**缓存未命中**） | 一次 LLM 调用同时产出新摘要 + 新画像 → SQLite 覆盖 + Chroma 摘要快照 + MD 审计 | — |
| 缓存命中（直接返回缓存答案） | **只**写短期记忆 + 话题计数（保证追问上下文连续） | **不读取**任何记忆（不走 LLM，无需注入） |

> 注意：**缓存命中和未命中是两套路径**。命中时不需要组装上下文，
> 所以不会触发记忆读取；但会写短期记忆，否则用户追问"你刚才说啥"时上下文断裂
> （这是缓存设计里专门补的一致性逻辑）。

**注入路由（读侧优化）**：纯闲聊（问候/寒暄）不注入画像和摘要——知识/业务
问题才需要用户画像与历史摘要；检测用轻量短语匹配（`_is_small_talk`），
不做 LLM 判断（每轮多一次调用比省下的 token 贵）。

**管理端人工纠错**：`GET/DELETE /api/admin/memory/{user_id}` 可查看当前画像、
最新摘要与人可读审计日志，删除单条偏好或一键清空记忆（清空会连同演进式摘要
一起删除，审计日志保留供追溯）。

**容量/淘汰**：短期记忆最近 N 轮满了挤掉最旧；摘要只保留最新一版（旧版在
Chroma 快照和审计 MD 里）；用户画像按条数/长度截断注入，SQLite 里保留全部
当前生效条目，历史在审计 MD。

## 记忆被污染了怎么办（诚实版）

面试常问"如果记忆里存了错误信息，后续任务被污染了，你怎么发现和修正"。当前系统
的能力边界如下：

- **可自愈的部分**：演进式摘要是覆盖式更新，新一轮摘要会替换旧摘要，错误信息
  会在后续摘要中被修正；用户画像的 key_facts 同样会被后续提取结果覆盖。
- **未闭环的部分**：ChromaDB 对话记忆只增不删，一旦写入错误片段，语义召回仍可能
  命中它；没有"纠错删除"和"过期衰减"机制。缓解手段是召回片段在 prompt 中明确
  标注"仅供参考"，并要求 LLM 以知识库检索结果为准。

  **"缓解手段"是什么意思**：没有根治（删除/过期错误记忆）手段时，降低错误
  记忆造成的危害：标注"仅供参考"让模型不把记忆当事实，要求以知识库检索为准
  让事实只信知识库。根治是"倒掉脏水"，缓解是"倒不掉时告诉喝水的人先过滤"——
  缓解不能保证 100% 不出错，只能压低污染概率。

- **发现手段**：评测低分告警 + 人工抽查 Badcase，定位到具体回答后再反查注入的
  记忆片段来源（`realtime_scores.json` 记录了 query/answer，可回溯）。

  **Badcase 怎么保留、什么时机、有没有提示**：

  - 落点：`data/eval_alerts.json`，每条含 query、answer、三维分数、阈值、
    explanation、timestamp，保留最近 200 条
  - 时机：每次回答后实时评测，有用性或相关性 < 3 时写入（每轮回答后触发）
  - 提示：管理后台仪表盘显示告警数量（红色标签）+ 告警列表接口；
    **没有主动通知**（无邮件/Webhook/站内推送），需人工打开后台查看
  - 回溯链路：告警的 query/answer/timestamp → 按时间反查会话记录 →
    人工判断是否记忆污染
  - **真实缺口**：评测记录里没有"本轮注入了哪几条记忆片段"的字段，
    定位到 badcase 后无法直接看到是哪条记忆带偏的；改进方向是评测埋点
    增加 `memory_context`（注入的回忆片段/画像/摘要），badcase 回流时可查

这个"诚实版"比硬吹更经得住追问——面试官追到第三层时，知道自己系统边界的人
反而更可信。
