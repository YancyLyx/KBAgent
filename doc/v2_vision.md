# V2 愿景：知识库资源化 —— 个人私库与共享市场

> 本文档是 V2 的产品与技术愿景规划，不是实现文档。目的：明确方向、固化关键设计决策，
> 供后续按阶段落地。状态：**规划中，未开始实现**。

---

## 1. 一句话愿景

让每个知识库成为**可发布、可订阅的独立资源**：个人拥有私库，可一键发布共享，
他人可下载/订阅——像把 skill 传到 GitHub 一样，把知识库变成"可分享的资产"。

## 2. 为什么（现状与痛点）

V1 的形态：一套共享知识库 + tag 分类，所有用户查询同一套文档，上传与管理集中在管理端。

三个痛点：

1. **知识库无法分享到"体系外"**：想把自己的优质文档给外部团队/朋友用，只能手动传文件
2. **没有个人知识空间**：用户只有"公共知识库"，无法建立自己的私库（个人笔记、部门专属资料）
3. **知识库不可复用**：别人精心整理的制度库/领域知识库，无法"下载即用"，只能重新上传+分块

V2 的机会：把知识库从"内容"升级为"资源"，复用 GitHub / skill 市场 / 插件市场的心智。

## 3. 核心概念

### 3.1 知识库包（Knowledge Base Package）

一个可分发的最小单元，zip 打包：

```text
kb-{id}.zip
├── manifest.json      # kb_id、名称、说明、tag、版本、作者、可见性、导出时间
└── docs/              # 文档原文（md/pdf/txt）
```

导入时走 V1 现有管线重新分块 + embedding（可移植性最好，不依赖向量格式兼容）。

### 3.2 三个角色视角

| 视角 | 能力 |
------|------|
| 创建者 | 建私库、上传文档、管理内容、一键发布（导出包 / 标记 public） |
| 订阅者 | 浏览公共市场、搜索、一键导入到自己的空间、管理已订阅库 |
| 平台（管理员） | 内容治理、下架违规库、统计订阅/下载量 |

### 3.3 权限模型

```text
private      仅 owner 可见（复用 V1 的 user_id 隔离 + token 鉴权）
public       所有人可见、可下载/订阅
shared-link  （未来）带 token 的分享链接，指定人可访问
```

## 4. 关键设计决策（先定方向再动手）

### 决策 1：共享用"复制"还是"引用"？

| | 复制（导出/导入） | 引用（订阅挂载） |
|---|---|---|
| 做法 | 发布者导出 zip，订阅者下载后导入自己空间重建索引 | 服务端共享一份索引，订阅者获得访问权限 |
| 类比 | GitHub 下载 zip / fork | 依赖包 / 关注订阅 |
| 更新同步 | 不自动（需重新下载新版本） | 自动（发布者更新所有人可见） |
| 实现成本 | 低 | 高（共享索引 + 权限校验 + 更新通知） |

**结论：V2.0 先做"复制"（导出/导入）**，离线可移植、心智简单；"引用"作为 V2.2。

### 决策 2：向量隔离用"一个 collection + kb_id 维度"还是"每库一个 collection"？

| | 单 collection + kb_id 过滤 | 每库一个 collection |
|---|---|---|
| 优点 | 检索一次全库、BM25 一份、运维简单 | 隔离彻底、可单独删除/迁移 |
| 缺点 | 过滤维度多了 kb_id，检索要带两重条件 | 库多了 collection 爆炸、BM25 每库一份 |

**结论：V2.0 用"单 collection + kb_id 元数据维度"**（检索时 where 同时带 kb_id + tag），
每库 collection 留作未来隔离需求时的迁移路径。

### 决策 3：导入导出格式

- 导出 = 文档原文 + manifest（不含向量，保证跨环境可移植）
- 导入 = 校验 manifest → 走 V1 分块/embedding 管线 → 写入 kb_id 维度
- 版本号递增，订阅者升级 = 重新导入新版本包（复制模型的自然结果）

## 5. 分阶段路线

### 阶段 1：知识库实体化 + 导出/导入闭环（V2.0）

目标：让"我的私库 → 导出包 → 别人导入"这条链路跑通。

- 数据模型：`knowledge_base` 增加 kb_id / owner_id / visibility / version
- 用户端"我的知识库"页面：建库、上传、管理（复用 V1 上传/分块管线）
- 导出 API：`GET /api/kb/{id}/export` → zip
- 导入 API：`POST /api/kb/import`（zip 上传）→ 自动分块入库
- 权限校验：私库导出/管理仅 owner，公共库可导入

交付物：导出 zip 在另一个账号导入后检索正常。

### 阶段 2：公共市场（V2.1）

目标：可发现、可搜索、可一键订阅。

- 公共知识库列表 + 搜索（名称/tag/说明）
- 一键导入（订阅）到自己的空间，已订阅列表管理
- 导出记录/订阅统计（供管理端治理）

交付物：市场页能搜到公共库并一键导入。

### 阶段 3：引用模型（V2.2，可选）

目标：订阅者的库与发布者同步更新。

- 服务端共享索引 + 订阅关系表
- 发布者更新 → 订阅者检索自动使用新版本
- 版本回滚、变更日志

交付物：订阅库跟随发布者更新，无需重新导入。

## 6. 对现有架构的影响

**复用（改动小）**：
- 上传 → 分块 → embedding → 入库管线（V1 已有）
- 用户隔离与鉴权（user_id + HMAC token + 管理端登录）
- Skill 系统（tag → 知识库包的元数据）
- 管理端文档管理页（扩展成"我的知识库"）

**需要新增**：
- 数据模型：kb 实体表（kb_id/owner/visibility/version/manifest）
- 检索过滤：where 增加 kb_id 维度（与现有 tag 过滤叠加）
- API：导出/导入/发布/市场列表/订阅
- 前端：用户端"我的知识库"页 + 市场页

## 7. 非目标（V2 明确不做）

- 不做支付/商业化（订阅计费）
- 不做复杂社交（评论/评分/关注关系）
- 不做向量级合并/去重（导入以文档为单位，不跨库合并）
- 不做私有化部署形态（仍是共享服务，本地工具形态另立项目）

## 8. 价值

**产品价值**：知识库从"平台内容"变为"用户资产"，形成"建库 → 发布 → 订阅"的生态；
优质知识可复用，降低重复建设成本。

**技术价值/面试价值**：多租户资源模型 + 权限体系 + 导入导出 + 市场检索，
是比"单套知识库"强得多的系统设计题目——能讲清楚"复制 vs 引用"、
"单 collection + kb_id vs 每库 collection"、"导入即重建索引的可移植性"，
都是面试官愿意深挖的点。
