# LLM-as-Judge 与三层评估体系

> 目标读者：回答"怎么评估效果"这道题的人。
> 本文档按第三篇面经的"三层金字塔"组织：分环节指标 → 主观量化 → 业务收口。

---

## 0. 破题："主观"不等于"没指标"

问答 Agent 的输出是自然语言，天然有主观性，但"主观"和"没有指标"是两回事。
成熟评估体系的核心动作是：**把主观感受翻译成可复现、可追踪、可对比的量化
指标**。面试官想听的是这个"翻译"过程，而不是"人工看效果"。

---

## 1. 第一层：分环节评估

为什么分环节：答案不好，可能是检索没召回对的资料，也可能是生成拉胯。
混在一起打分，找不到病根。分环节后，每一节单独挂指标，哪节掉链子一眼可见。

### 1.1 检索环节三把尺子

| 指标 | 一句话定义 | 它看什么 / 低了意味着什么 | 项目数字 |
|---|---|---|---|
| HR@k | 正确答案出现在前 k 个结果里的问题占比 | 该找的有没有找到；低了是召回问题 | 纯向量 HR@1 82.09% → 混合 85.07% |
| Precision@k | top-k 中与答案相关的文档占比 | 召回里有多少噪音；低了是 Rerank/Embedding 区分度不够 | 新增指标，随评测脚本输出 |
| MRR | 正确答案排位的倒数均值 | 排序质量；低了是排序不行，命中了模型也未必用得上 | 0.8799 → 0.8986 |
| P50 | 延迟中位数 | 典型响应速度 | 6.8 / 17.2 / 265.6 ms |

**为什么能脱离生成模型跑**：检索层是纯 IR 问题——准备"问题-标准文档"对照表，
自动跑 HR/MRR/Precision，不依赖大模型随机性。所以检索层优化可以做"改了就能
看到反馈"的闭环（每次改分块/换 embedding/调 Rerank 立刻出数字）。

**Precision@k 在本项目的定义**：QA 是"单答案"（answer_gt 为原文片段），
所以相关文档数 = 命中该片段的 chunk 数；P@k 在此场景衡量的是**噪音稀释程度**。

#### Recall 和 HR@k 的关系（面试高频追问）

第三篇面经讲检索"三把尺子"用的是 **Recall / Precision / MRR**，而本项目跑的是
**HR / MRR / Precision**。两者不矛盾，区别在评测集的标注粒度：

| 指标 | 定义 | 需要什么标注 | 适用场景 |
|---|---|---|---|
| Recall@k | 标准答案文档集里，被 top-k 召回的占比 | 每个问题标注**多个**相关文档 ID | 多相关文档（一题能由多篇文档回答） |
| HR@k（Hit Rate@k） | top-k 里**至少出现一个**正确答案的问题占比 | 每个问题一个"正确答案片段" | 单答案 QA |

**为什么本项目用 HR 而不是 Recall**：test-corpus 的 QA 是"问题-原文片段"
单答案标注（答案子串在不在检索结果里），天然只有"命中/未命中"二值，
HR 就是它的正确度量。**单答案场景下 HR@k ≈ 退化的 Recall@k**（分子恒为
0 或 1）。

**面试答法**：被问"为什么不用 Recall"→ 答"我们的评测集是单答案标注，
HR 是 Recall 在该标注粒度下的退化形式；如果换成多相关文档标注（一题对应
多篇文档 ID），就改用 Recall@k + Precision@k，脚本已支持两种口径"。
（诚实边界：test-corpus 目前没有多相关文档标注，Recall 是演进方向。）

### 1.2 生成环节三件套 + 一维

| 维度 | 一句话定义 | 低意味着什么 / 怎么修 |
|---|---|---|
| 忠实度（Faithfulness） | 答案是否严格基于检索资料，有无编造 | 幻觉——RAG 最致命失败模式；改 Prompt 约束/加引用/Self-Check |
| 相关性（Relevance） | 是否答了用户真正问的问题 | 答非所问；改查询改写/强化聚焦指令 |
| 完整性（Completeness） | 是否覆盖所有关键信息 | 漏点；扩大检索/调整 prompt |
| 有用性（Usefulness） | 是否切实解决问题 | 兜底重答 |

**第三篇讲的是"忠实度/相关性/准确率"三件套，为什么我们还加了完整性/有用性**：
准确率（Accuracy）是最难自动化的维度——它要判断"内容对不对"（数字、事实、
流程），需要一个**标准答案（Golden Answer）**做参照，而业务领域往往没有现成
标准答案。我们的做法是用"完整性 + 有用性"近似：完整性管"该说的说全了没"，
有用性管"能不能落地"。诚实边界：**准确率没有单独设维度**。

**如果面试官问"准确率怎么测"**（知识科普 + 方案）：
- 有 Golden Answer 的场景：LLM-as-Judge 把回答与标准答案对照打分（事实核对）
- 没有标准答案的场景：人工抽检 + 业务方校验（领域专家确认数字/条款对错）
- 工程化方案：为高频问题建立"标准答案库"，定期跑"回答 vs 标准答案"的
  一致性核对，准确率低的 query 人工复核后回流

**维度间的三角权衡**（面试加分）：

```text
忠实度（只引用资料） ←→ 相关性（敢归纳）
    ↑
准确率（内容必须对）
```

Prompt 写得太严（只能逐字引用）→ 忠实度上去了、相关性下来（不敢归纳）；
太松 → 相关性上去、忠实度下来（开始编）。评估体系要能看到这种权衡，
而不是只盯一个维度。

**为什么不能合并成一个"答案好不好"的总分**：三个维度指向的优化动作完全不同，
混在一起拿到"3.2 分"不知道该往哪使劲。分开打分，问题出在哪一节清清楚楚。
（忠实度需要参考文档才能评，所以 `Evaluator.evaluate(query, answer, contexts)`
在传检索上下文时才评忠实度。）

**维度间有权衡**：Prompt 写得太严（只能逐字引用）忠实度上去、相关性可能下来
（不敢归纳）。评估体系要能看到权衡，不是单点最优。

### 1.3 交互环节指标

| 指标 | 项目实现 |
|---|---|
| 工具调用成功率 | `metrics.record_request` 记录 tool_calls/tool_failures，`summary()` 输出调用级成功率 |
| 缓存命中率 | request_metrics 聚合 cache_hit_rate |
| 告警率/兜底率 | eval_alerts + fallback 标记 |

## 2. 第二层：把"主观"翻译成结构化数据

### 2.1 Rubric（评分标准逐维定义）

评分 prompt 把每个维度写成可判断的标准（1-5 分），让不同标注员对同一条答案
能打出接近的分——Rubric 不具体，本身就变成新的主观源。

**Rubric 设计的四个原则**（面试深挖点）：

1. **维度独立**：每个维度只衡量一件事，不重叠。相关性看"答没答对题"，
   完整性看"说全没说全"，混在一起没法定位问题。
2. **档位有锚定描述**：每个分数档位要有"看到什么特征给几分"的描述，
   而不是"好=5 分"。档位锚定是标注员一致性的基础。
3. **与 Judge 的 prompt 严格对齐**：LLM-as-Judge 用的 Rubric 必须和人工标注
   用的是同一套——否则 LLM 和人工打的是两套标准，一致性校准永远过不了。
4. **先小样校准再推广**：先让两个标注员在 30-50 条样本上独立打分，
   算一致性（Kappa），不一致的维度先修 Rubric 再推广到全量。

**档位锚定示例（以相关性 1-5 分为例）**：

```text
5 完全命中：直接回答用户问题，无冗余、无偏题
4 基本命中：回答了核心问题，但有小偏差或多余铺垫
3 部分命中：沾边但没答到点上（用户问"流程"，答了"政策"）
2 偏题：答的是另一个问题，或夹带大量无关内容
1 完全跑题：与问题无关
```

面试被问"Rubric 怎么设计"就按四原则 + 档位锚定讲，比"就是打分标准"深一层。

### 2.2 LLM-as-Judge 与一致性校准

**做法**：用独立评测模型（`EVAL_MODEL` 可配，与回复模型解耦）按 Rubric 打分；
传检索上下文时额外评忠实度。支持 `Evaluator.compare()` 做 Pairwise 两两比较
（相对判断比绝对打分更稳）。

**必须做一致性校准（面试分水岭）**：LLM Judge 不是黑箱。脚本
`scripts/eval_judge_calibration.py` 就绪，做两件事：
- 人工标注一致性：同批样本人工 vs Judge 逐维算 Cohen's Kappa + Pearson，
  业界经验阈值 Kappa ≥ 0.6-0.7
- Judge 稳定性（test-retest）：同一批样本跑两遍，算一致比例与 Kappa

**诚实边界（主动讲）**：校准数字需要人工标注样本（建议 ≥30 条），
本项目尚未标注，所以**没有产出校准结论**——脚本可用，数字待补。

**LLM-as-Judge 的已知偏差（知识科普，被问"Judge 有什么坑"时用）**：

| 偏差 | 现象 | 缓解 |
|---|---|---|
| 位置偏差 | 两个回答里 A/B 的顺序影响胜负判断 | Pairwise 交换顺序跑两遍，取一致结果 |
| 冗长偏差 | 更长的回答更容易得高分（哪怕废话多） | Rubric 里明确"简洁性"，或限制长度 |
| 自我偏好 | 与 Judge 自己风格接近的回答得分更高 | 换不同家族的 Judge 交叉验证 |
| 权威偏差 | 语气笃定/带引用的回答更容易高分 | 对"无中生有的引用"专门降分（忠实度维度） |

**校准不通过怎么办**（面试问"Kappa 低于 0.6 呢"）：
先查 Rubric 是否和人工一致（最常见原因）→ 换更强的 Judge 模型 →
维度拆分更细 → 还不行就降低该维度的自动化权重、改人工抽检。

**Pairwise 两两比较**：`Evaluator.compare(query, answer_a, answer_b, contexts)`
返回 {"winner": "a"/"b"/"tie", "reason"}。相对判断（谁更好）比绝对打分
（打几分）更稳定，适合策略对比（精排开/关、Autocut 开/关、Prompt A/B）——
一次对比一批答案，统计胜率，比平均分差异更可信。

### 2.3 Golden Set（标准评估集）

**什么是 Golden Set / Eval Set**：一个**固定的、有代表性的测试问题集**。
每次模型/Prompt/检索策略迭代后，都在这个固定集合上跑一遍，形成可对比的
历史趋势曲线——而不是每次都凭感觉说"看着还行"。

**为什么必须"固定"**：评估集一旦变动，跑分结果就没有可比性——今天 90 分
可能是"集子变简单了"而不是"系统变好了"。固定集合 + 锁版本是历史可比性的
前提。

#### 四类问题覆盖（Golden Set 设计的第一要务）

| 类别 | 覆盖什么 | 为什么必须有 | 例子（制度文档场景） |
|---|---|---|---|
| **高频问题** | 业务里 Top 80% 流量的问题 | 评估要反映真实使用分布，否则跑分与线上脱节 | "年假多少天""报销流程是什么" |
| **长尾问题** | 罕见但重要的边界条件 | 高频覆盖不到的系统短板都藏在这里 | "出差当天航班取消住宿费谁出" |
| **陷阱问题** | 容易诱发幻觉/需多步推理/容易答非所问 | 专测系统最怕的失败模式 | "试用期有没有年假"（检索结果没直接答案，逼模型要么说不知道要么编） |
| **安全问题** | 合规/敏感/越界，Agent 必须正确拒绝 | 编错一句可能引发合规或业务损失 | "离职赔偿金最低能给多少"（涉及谈判空间，应拒绝或转人工） |

#### 规模：200-500 条是甜区

- **太小（<100）没统计意义**：单条 badcase 就能让指标掉 1-2 个百分点，
  方差大、噪音多，改一个检索策略看不出真实差异
- **太大（>1000）维护吃力**：每条要维护标准答案、标注文档 ID、定期复核，
  维护成本指数级上升，容易陷入"标准答案过期但没人改"的烂摊子
- **本项目现状**：67 条偏小，且未按四类标注——诚实边界，扩展集待建

#### 版本管理（Golden Set 的工程纪律）

1. **老问题锁版本**：已入库的问题和标准答案一旦定下来不能改——改了破坏
   历史可比性
2. **新增走扩展集**：新问题单独加到扩展集（Eval Set v2、v3…），跑分时
   主集 + 扩展集分开报，主集保可比性、扩展集验增量
3. **标准答案锁定**：如果领域知识更新导致旧答案过期，不是改旧问题，而是
   新增"更新版"问题，旧问题保留标注"已过期不参与聚合"或整体移入归档集

#### 面试答法：给你时间做一个评测集，你怎么做

按这个五步回答（知识汇总，从容应对）：

```text
第一步 定范围：先拉线上真实 query 日志，统计 Top 高频问题（覆盖 80% 流量），
        再人工挑长尾/边界/陷阱/安全四类补充
第二步 定答案：每条问题标注标准答案；能原文定位的自动判定命中，
        需要推理的走 Golden Answer + 人工复核
第三步 定规模：目标 200-500 条，先 100 条起步跑通流程再扩展
第四步 锁版本：主集锁版本，新增走扩展集，历史可比性优先
第五步 挂 CI：检索层指标每次提交自动跑（秒级），生成层 nightly，
        形成趋势曲线；badcase 回流补进扩展集
```

**我们做了一半**：67 条 QA + 自动命中判定 + 离线脚本（第一步/第二步/第五步
的部分）；缺口是规模（67 → 200+）、四类标注、扩展集版本管理——面试要主动
说"这是演进方向"，比被追问出来体面。

#### 本项目现状速览

| 原则 | 现状 |
|---|---|
| 覆盖高频问题 | ✅ 制度常见问题（报销/年假/考勤） |
| 覆盖长尾问题 | ✅ 部分边界条件 |
| 覆盖陷阱问题 | ⚠️ 未分类标注 |
| 覆盖安全问题 | ⚠️ 未分类标注 |
| 规模 200-500 | ⚠️ 67 条偏小，扩展集待建 |
| 版本管理（锁版本/扩展集） | ⚠️ 未建立 |

## 3. 第三层：业务指标收口（"所以呢"）

技术指标做得再漂亮，业务方关心结果。传导链：

```
Recall↑ → 准确率↑ → 解决率↑ → 升级率↓ → 成本↓
```

四类业务指标：满意度（CSAT/NPS/点赞率，看趋势不看绝对值）、解决率（FCR/
任务完成率）、升级率（人工升级率/投诉率）、成本（单次会话成本/Token）。

**诚实边界（主动讲）**：单机项目没有真实用户流量，满意度/解决率/升级率
**没有产出数字**。能讲的是：这套评估体系上线后如何挂这些指标（埋点已支持
token 成本、工具成功率、告警率），以及四类指标之间的张力（压升级率满意度可能
掉，答案更详细 token 成本上升）——评估收口的本质是在四类指标间找均衡点。

## 4. 实时评测链路（低分 → 告警 → 兜底 → 回溯）

```
用户提问 → Agent 处理 → 返回回答
  → Evaluator.evaluate(query, answer, contexts=检索结果)
     四维评分：相关性 / 完整性 / 有用性 / 忠实度（有上下文时）
  → 存入 data/realtime_scores.json（含 memory_context 与 faithfulness）
  → 任一维度 < 3 → 告警（eval_alerts.json）
      → 兜底：复用已有 pipeline 扩大检索（去掉 tag 限制、top-5）
             + 首轮检索结果一并拼上下文 → 重新生成
             → 兜底答案不写缓存
  → 低分告警的 query/answer/memory_context 可回溯 badcase
```

**为什么传 contexts 评忠实度**：忠实度的定义是"答案是否基于检索资料"，没有
参照物无法评。传 `last_tool_result`（本轮检索结果）后，Judge 能判断
"这段答案是检索来的还是编的"。

**badcase 回溯闭环**：告警记录含 query/answer/三维分数/忠实度/注入的记忆片段
（memory_context）——定位"是不是某条记忆污染带偏了回答"成为可能。

### 低分长什么样（两个真实形态的示例）

示例一：**完整性低（信息不全）**

```text
用户问题：出差住酒店能报多少钱？
AI 回答：可以报销。（相关性 4，完整性 1，有用性 1）
→ 完整性/有用性 < 3 → 告警
→ 兜底：扩大检索（top-5、去掉 tag 限制）+ 首轮检索结果拼入
→ 重答："出差住宿费按城市标准报销，一线城市每晚不超过 500 元……"
```

示例二：**忠实度低（编造）**

```text
用户问题：试用期员工有没有带薪年假？
检索片段：年假资格自转正后按工龄计算（片段里没有"试用期"相关内容）
AI 回答：试用期员工不享受带薪年假，且年假按入职首年折算。
        ↑ "按入职首年折算"在检索片段里找不到依据 —— 编造
Judge（传检索上下文）→ 相关性 4、忠实度 2 → 忠实度 < 3 触发告警
```

这两个示例说明为什么"三维/四维不能合并"：示例一该扩检索（检索问题），
示例二该加引用约束（生成问题）——合并成"4.2 分"就不知道该修哪。

## 5. 工程取舍（六条，架构师视角）

### 取舍一：自动 vs 人工的投入配比

**为什么不能全自动**：LLM Judge 对"语气得体、用户友好"这类软性维度判断不稳，
对领域专业准确率也会翻车——纯自动评估有死角。业界常见配比：人工 20% /
LLM 60% / 争议双盲 20%。一开始就把人工压到 5% 以下，长期埋雷。
**本项目现状**：全自动（LLM Judge）+ 低分告警人工抽查入口，双盲复核未建。

### 取舍二：Golden Set 规模 vs 维护成本

200-500 条是大多数团队的甜区；超过 1000 维护开始吃力（标准答案过期没人改）。
新增走扩展集、老问题锁版本是保持可比性的唯一办法。
**本项目现状**：67 条，扩展集待建（详见 2.3）。

### 取舍三：Judge 模型选择与成本

GPT-4 级别最稳但 token 贵（500 条一次几十块）；小模型便宜但一致性不够。
中间路线：中等模型初筛 + 争议样本回流强模型复核。
**本项目现状**：EVAL_MODEL 独立配置（可用更便宜的模型控成本），
与回复模型解耦；"初筛+复核"未实现。

### 取舍四：评估频率 vs 迭代节奏

理想是每次提交都跑全量，但 LLM Judge 的延迟和成本扛不住。三档节奏：
**检索层 CI 自动（秒级，纯本地无 LLM）→ 生成层 nightly（分钟级）→
业务指标周报（天级，依赖真实流量）**。
**本项目现状**：离线脚本可挂 CI（未实际挂）；批量 Judge 脚本 nightly 可跑；
业务周报需线上流量（无）。

### 取舍五：在线 vs 离线评估的边界

离线（Golden Set + Judge）回答"能不能上线"，在线（A/B + 实时指标）回答
"上线后怎么样"，两者不能互相替代——离线全绿但上线翻车比比皆是（Golden Set
覆盖不了真实长尾问法）。**离线是门槛，在线是裁判**，跳过在线直接全量等于裸奔。
**本项目现状**：只有离线，A/B 是演进方向（诚实标注）。

### 取舍六：告警阈值怎么定

阈值太严天天误报、太松问题漏掉。经验：**分维度设阈值**（忠实度掉 5% 告警、
相关性掉 10% 告警、满意度掉 0.2 告警），基于历史基线方差来定，第一版定松
一点、跑一个月看真实波动再收紧。
**本项目现状**：绝对阈值（任一维度 <3 告警）；基线方差驱动的漂移告警是
演进方向。

## 6. 面试话术（三层结构 + 一升华）

> 第一层（基本原理）：主观是客观存在的，但成熟做法是分层拆解——检索/生成/
> 交互三环节各挂独立指标，检索看 HR/MRR/Precision，生成看忠实度/相关性/
> 完整性/有用性，交互看工具成功率。
> 第二层（细节为什么）：分开是因为混在一起打分找不到病根；主观评估要结构化
> 是因为笼统打分不可复现；LLM Judge 要一致性校准是因为不校准就是另一个黑箱。
> 第三层（设计哲学）：评估的本质不是"测准不准"，而是把主观感受翻译成可追踪
> 的数据——翻译能力才是工程化的核心。
> 升华：技术指标最终收口到业务指标（满意度/解决率/升级率/成本），
> 形成"技术驱动业务"的闭环。

**加分项**：一致性校准、Golden Set 四类覆盖（诚实说缺口）、离线 vs 在线边界、
指标权衡。
